# Docker 핵심 개념 정리

## Docker 정의

애플리케이션을 신속하게 구축, 테스트 및 배포할 수 있는 소프트웨어 플랫폼

<aside>
💡

Docker 는 원래 화물 운송에서 유래한 용어로, 화물을 배에서 배로 옮기는 작업자(docker) 를 의미한다.

</aside>

**화물 운송과 Docker 용어 비교**

| 화물 운송 | 의미 | Docker / IT |
| --- | --- | --- |
| 화물 | 운송 대상 | 애플리케이션 |
| 컨테이너 | 화물을 담는 표준 박스 | 컨테이너(Container) |
| 항구 | 출발·도착 지점 | 서버 / 실행 환경 |
| 바다 | 운송 경로 | 네트워크 |
| 작업자 | 컨테이너를 옮기는 주체 | Docker 엔진 |

![image.png](/posts/docker/basic/image.png)

## 컨테이너 정의

리눅스 OS 위에서 격리된 환경을 제공받는 프로세스

<aside>
💡

**컨테이너는 리눅스에 있는 개념으로 리눅스에서 격리된 프로세스를 말하고, Docker는 이를 네트워크 위에서 쉽게 옮기게 해주는 도구이다**

</aside>

**VM vs 컨테이너 비교**

| 구분 | VM | 컨테이너 |
| --- | --- | --- |
| OS | 각 VM마다 OS 필요 (커널 존재) | 호스트 OS 공유 |
| 부팅 | 느림 (부팅 과정 존재) | 빠름 (프로세스 실행) |
| 성능 | 성능 손실 있음 | 성능 손실 거의 없음 |
| 무게 | 무거움 | 가벼움 |

![image.png](/posts/docker/basic/image%201.png)

## 컨테이너 기반 기술

### Namespace

- 같은 OS를 사용하지만, **각자 독립된 환경처럼 보이게 만드는 격리 기술**
- 실제로는 커널을 **공유**하지만 프로세스는 **자기 것만 존재한다고 인식**

**Namespace 종류**

| 네임스페이스 | 설명 |
| --- | --- |
| IPC | 공유 메모리, 메시지 큐, 세마포어 등 IPC 자원을 컨테이너별로 분리 |
| Network | 네트워크 인터페이스, IP, 포트, 라우팅, 방화벽 규칙을 컨테이너별로 분리 |
| Mount | 파일 시스템 마운트 지점을 분리하여 컨테이너마다 독립된 파일 시스템 뷰 제공 |
| PID | 프로세스 ID 공간을 분리하여 각 컨테이너가 자체 PID 1(init)을 가짐 |
| UTS | hostname과 NIS 도메인 이름을 컨테이너별로 독립적으로 설정 |
| User | 사용자 및 그룹 ID를 분리하여 컨테이너 내부 root를 호스트와 분리 |

### cgroup(Control Group)

- **프로세스가 사용하는 시스템 자원(CPU, 메모리, 디스크, 네트워크 등)을 제한·관리하는 기능**

## Linux Netfilter Subsystem

- 리눅스 커널 내부의 네트워크 관련 프레임워크
- 다양한 네트워크 관련 연산을 핸들러 형태로 구현할 수 있도록 훅(hook)을 제공 (허용/차단/수정 가능)
- 패킷 후킹
    - 패킷 흐름 중 **지정된 지점에서 패킷을 가로채는 구조**
    - Netfilter는 패킷을 여러 **Hook Point**에서 검사
- **Netfilter의 역할**
    - 방화벽 기능
    - 패킷 필터링
    - NAT (주소 변환)
    - 포트 포워딩
    - 패킷 수정 및 로깅
- **iptables**
    - Netfilter를 사용자가 제어하는 대표 도구

<aside>
💡

도커 사용시

- 커널의 기능들을 편리하게 사용 가능
- Docker는 자동으로 **iptables 규칙 생성**
- 컨테이너 포트 포워딩 = Netfilter NAT 사용
</aside>

# 컨테이너, 이미지, 볼륨 사용법

## 용어 정리

![image.png](/posts/docker/basic/image%203.png)

- **Image:** 컨테이너를 만들기 위한 **실행 템플릿(설계도)**
- **Container:** Image를 실행한 **런타임 인스턴스**
- **Registry:** Image를 저장·공유하는 **중앙 저장소 (ex. Docker Hub)**
- **Repository:** 특정 Image들의 **버전 묶음 공간**
- **Tag:** Image의 **버전 식별자** (ex. nginx:latest)

## 1. 컨테이너

### 컨테이너 라이프 사이클

- **create**: 컨테이너 껍데기 생성
- **start**: 생성된 컨테이너 실행
- **stop**: 정상 종료
- **rm**: 컨테이너 삭제
- **run**: create + start를 한 번에 수행

![image.png](/posts/docker/basic/image%204.png)

### 컨테이너 실행

| **옵션** | **의미** | **예시** |
| --- | --- | --- |
| --name | 컨테이너 이름 지정 | docker run -d --name web nginx |
| -it | 터미널(stdin + tty) 연결 | docker run -it --name test ubuntu:24.04 |
| -d | 백그라운드(데몬) 실행 | docker run -d --name api my-api:1.0 |
| -p H:C | 호스트 포트 → 컨테이너 포트 매핑 | docker run -d --name web -p 80:8080 myapp |
| -v H:C | 호스트 디렉토리 → 컨테이너 디렉토리 마운트 | docker run -d --name db -v /data/mysql:/var/lib/mysql mysql:8 |
- 백그라운드 실행 중일 때 터미널 접속법
    
    ```bash
    docker exec -it web /bin/bash
    ```
    

## 2. Image

### UFS(Union File System)과 Layer

![image.png](/posts/docker/basic/image%205.png)

- **Image**
    - 컨테이너 실행을 위한 기반을 제공하는 읽기전용 템플릿
- **Layer**
    - 이미지는 연결된 여러 레이어로 구성됨
    - 레이어는 읽기전용이며, 이미지 다운로드시 기존 레이어를 재활용하며 변경 부분만 다운로드
- **UFS**
    - union mount를 구현하고 Layer를 생성하여 작동하는 파일 시스템
        - union mount
            
            여러 개의 폴더(레이어)를 겹쳐서 하나의 폴더처럼 보이게 만드는 마운트 방식
            
    - 도커는 copy-on-write와 UFS를 사용하여 가볍고 빠르게 동작
- **컨테이너와 쓰기 가능 레이어**
    - 컨테이너가 생성되면 최상위에 쓰기 가능한 레이어가 생성되고, 컨테이너에서 변경된 파일을 이 레이어에 저장

| **목적** | **명령어** |
| --- | --- |
| 이미지 목록 | docker image ls |
| 이미지 다운로드 | docker image pull nginx:latest |
| 레이어 확인 | docker image history nginx |

### **이미지 배포 & 이동**

![image.png](/posts/docker/basic/image%206.png)

### 흐름

<aside>
💡

**tag → push → pull**

</aside>

- **tag**: 이미지에 “이름/버전 라벨” 붙이기
- **push**: 내 로컬 이미지를 레지스트리(Docker Hub 등)에 업로드
- **pull**: 레지스트리에서 이미지 다운로드
    - **이미 있는 레이어는 재사용**하고, **없는 레이어만 다운로드**

| **목적** | **명령어 예시** | **포인트** |
| --- | --- | --- |
| 이미지 받기 | docker pull nginx:latest | 레지스트리 → 로컬 |
| 이미지 태그 붙이기 | docker tag myapp:1.0 myrepo/myapp:1.0 | push 전에 repo/name:tag 형태로 맞춤 |
| 이미지 올리기 | docker push myrepo/myapp:1.0 | 로컬 → 레지스트리 |
| 로컬 이미지 확인 | docker image ls |  |

## 3. volume

### 볼륨이 필요한 이유

컨테이너에서 생성/수정한 파일은 기본적으로 CoW(Copy-on-Write) 레이어에 저장됨.

→ 컨테이너가 없어지면 데이터가 지속되지 않음

<aside>
💡

컨테이너가 삭제되거나 비정상일 때도 업로드한 파일을 안전하게 보존하는 방법은?

</aside>

![image.png](/posts/docker/basic/image%207.png)

1. **bind mount**
2. **⭐️ volume**
3. **tmpfs mount**

### **3-1) Bind mount (호스트 디렉토리 직접 마운트)**

- **호스트 디렉토리 ↔ 컨테이너 디렉토리**를 직접 연결
- 호스트 파일을 수정하면 컨테이너에서도 바로 반영되는 구조

```bash
docker container run -v <호스트 경로>:<컨테이너 마운트 경로>
```

### **3-2) Docker Volume (도커가 관리하는 저장소)**

- HOST 시스템의 /var/lib/docker/volumes 하위에 볼륨이 생성됨
- **⭐️ 가장 추천하는 방법**

```bash
# 이름 없는 볼륨 생성
docker container run에  -v <컨테이너 마운트 경로>
# 이름 있는 볼륨 생성
docker volume create <이름>
```

### **3-3) 데이터 전용 컨테이너**

- 실행 안 해도 생성만 되어 있어도 볼륨 공유됨
- 다른 컨테이너에서 --volumes-from dataOnlyCon 로 공유
    
    ![image.png](/posts/docker/basic/image%208.png)
    

```bash
# 1) 데이터 전용 컨테이너 생성(볼륨만 가진 컨테이너)
docker container create --name dataOnlyCon -v /upload busybox

# 2) 볼륨을 공유해서 사용하는 컨테이너 실행
docker container run -it --name app1 --volumes-from dataOnlyCon busybox sh
```

# Docker Network 정리

## Docker Network 개요

Docker는 컨테이너 간 및 외부와의 통신을 위해 **표준화된 네트워크 모델**을 사용한다.

### CNM (Container Network Model)

- Docker에서 제안한 **오픈소스 컨테이너 네트워크 모델**
- 컨테이너 네트워크의 기본 구성 요소를 정의

![image.png](/posts/docker/basic/image%209.png)

## Docker 네트워크 종류

### 1. bridge network (기본 네트워크)

- Docker 설치 시 기본으로 생성됨
- 호스트의 물리 NIC가 `docker0` 가상 브리지에 연결됨
- 컨테이너 실행 시 자동 할당
    - IP 대역: `172.17.0.0/16`
    - 인터페이스: `eth0`
- 컨테이너 간 통신 가능
- 외부 접근 시 **포트 매핑 필요**
    
    ```bash
    docker container run -p 80:8080
    ```
    
- 컨테이너 고정 IP 할당 불가

![image.png](/posts/docker/basic/image%2010.png)

### 2. host network

- 호스트의 네트워크를 **컨테이너와 공유**
- 네트워크 네임스페이스 격리 해제와 동일
- 브리지 네트워크를 거치지 않음
- 네트워크 성능 가장 빠름
- 포트 매핑 불필요 (포트 충돌 가능성 존재)
- 컨테이너가 root 권한일 경우 **호스트 네트워크에 직접적인 영향 가능**
- 보안상 위험 요소 존재

![image.png](/posts/docker/basic/image%2011.png)

### 3. none network

- 네트워크를 전혀 사용하지 않는 컨테이너
- loopback 인터페이스만 존재
- 완전 격리 환경
- 보안 테스트
- 네트워크 불필요한 작업

### 4. custom bridge network (사용자 정의 네트워크)

- 기본 bridge보다 **권장되는 방식**
- Linux bridge가 호스트에 생성됨
- 컨테이너 이름 기반 DNS 제공
- 수동 IP / 서브넷 지정 가능
- NAT 및 라우팅 지원
- 서브넷 미지정 시 IPAM 드라이버가 `172.18.0.0/16`부터 순차 할당

![image.png](/posts/docker/basic/image%2012.png)

### 5. overlay network

- 멀티 도커 호스트 간 네트워크
- 단일 호스트 bridge 네트워크의 한계를 해결
- 여러 서버의 컨테이너를 하나의 네트워크처럼 연결
- 분산 시스템 및 오케스트레이션 환경에서 사용

![image.png](/posts/docker/basic/image%2013.png)

## 네트워크 종류 요약

| 네트워크 | 특징 | 사용 목적 |
| --- | --- | --- |
| bridge | 기본 네트워크, 포트 매핑 필요 | 단일 호스트 컨테이너 통신 |
| host | 호스트 네트워크 공유 | 고성능, 테스트 |
| none | 네트워크 미사용 | 완전 격리 |
| user-defined bridge | DNS 지원, 설정 유연 | 실무 권장 |
| overlay | 멀티 호스트 | Swarm / Kubernetes |

## 네트워크 명령어

| 명령어 | 설명 |
| --- | --- |
| `docker network ls` | Docker 네트워크 목록 조회 |
| `docker network inspect <network>` | 네트워크 상세 정보 확인 |
| `docker network create <name>` | custom bridge 네트워크 생성 |
| `docker network rm <network>` | 네트워크 삭제 |
| `docker network prune` | 사용되지 않는 네트워크 전체 삭제 |
| `docker container run --network=bridge` | 기본 bridge 네트워크로 컨테이너 실행 |
| `docker container run --network=host` | host 네트워크로 컨테이너 실행 |
| `docker container run --network=none` | 네트워크 없이 컨테이너 실행 |
| `docker network connect <network> <container>` | 실행 중인 컨테이너를 네트워크에 연결 |
| `docker network disconnect <network> <container>` | 컨테이너를 네트워크에서 분리 |

### FROM

- 베이스 이미지 선택 (어떤 OS/런타임 위에서 실행할지 결정)

- 빌드 시 필요한 작업 실행

- RUN 스텝마다 cache에 저장하는데 --no-cache 옵션으로 캐시 사용 불가 설정 가능
    - `docker image build --no-cache`

| 기본 역할 | 파일/디렉터리 복사 | 파일 복사 + 추가 기능 |
| 로컬 파일 복사 | ⭕ | ⭕ |
| 디렉터리 복사 | ⭕ | ⭕ |
| 원격 URL 지원 | ❌ | ⭕ |
| 압축 파일 자동 해제 | ❌ | ⭕ (`.tar` 등) |
| 동작 예측성 | 높음 | 낮음 |
| 권장 사용 | ⭕ (권장) | ❌ (특수한 경우만) |

### CMD

- Dockerfile 내에 1번만 기술할 수 있고, 여러 번 기술되면 마지막 CMD 명령이 적용됨
- ENTRYPOINT 명령과 함께 사용되면 ENTRYPOINT의 파라미터값으로 전달됨
- 컨테이너 실행 시 오버라이드 할 수 있음

![image.png](/posts/docker/basic/image%2024.png)

### ENTRYPOINT

- 컨테이너 시작 시 자동으로 실행되는 명령을 지정할 때 사용
- CMD 명령과 함께 사용되면 CMD 명령의 값이 ENTRYPOINT 명령의 파라미터로 전달 됨
- CMD 명령과 다르게 컨테이너 실행 시 오버라이드 할 수 없음

![image.png](/posts/docker/basic/image%2025.png)

<aside>
💡

PID 1은 컨테이너가 시작될 때 가장 먼저 실행되고 종료되면 컨테이너도 함께 종료되는 메인 프로세스입니다. ENTRYPOINT는 PID1 을 지정하는 명령어입니다.

</aside>

### [예제]

1. **CMD 단독 사용 예제**

```docker
FROM openjdk:17
CMD ["java", "-jar", "app.jar"]
```

실행

```bash
docker run myapp
```

→ `java -jar app.jar`

오버라이드

```bash
docker container run myapp java -version
```

1. **ENTRYPOINT 단독 사용 예제**

```docker
ENTRYPOINT ["java"]
```

실행

```bash
docker container run myapp -version
```

→ `java -version`

👉 ENTRYPOINT는 **고정**, 뒤에 붙은 값은 인자

1. ENTRYPOINT + CMD 함께 사용하는 경우

```docker
ENTRYPOINT ["java", "-jar"]
CMD ["app.jar"]
```

실행

```bash
docker container run myapp
```

→ `java -jar app.jar`

CMD 오버라이드

```bash
docker container run myapp other.jar
```

→ `java -jar other.jar`

👉 **ENTRYPOINT는 유지, CMD만 변경**

# Compose

## 개념

- 여러 개의 컨테이너를 연동하는 경량의 오케스트레이션 툴

## 사용법

docker-compose.yml 파일을 구성하여 실행

**구성**

- 한 파일 안에 여러 컨테이너 설정 내용 저장
- 도커 애플리케이션을 위한 서비스, 네트워크, 볼륨을 정의
- 텍스트 파일 형태인 YAML 형식을 사용
- Version 3.x > Version 2 > Version 1
    - 각 버전에 맞게 지원하는 도커 엔진과 명령들이 상이함
    - compose file format 버전 3 주의 사항
        - links 항목의 기능은 version 1까지만 지원
        - scale, replicas 는 지원 안함
        - depends_on 항목의 condition은 지원 안함

![image.png](/posts/docker/basic/image%2026.png)

## 명령어

| 명령어 | 설명 |
| --- | --- |
| `docker compose up` | compose 파일 기반으로 서비스 실행 |
| `docker compose down` | 실행 중인 서비스 중지 및 컨테이너 제거 |
| `docker compose start` | 중지된 서비스 시작 |
| `docker compose stop` | 실행 중인 서비스 중지 |
| `docker compose restart` | 서비스 재시작 |
| `docker compose ps` | compose로 실행된 컨테이너 상태 확인 |
| `docker compose logs` | 서비스 로그 확인 |
| `docker compose exec <service> <cmd>` | 실행 중인 서비스 컨테이너에서 명령 실행 |
| `docker compose config` | compose 파일 문법 및 설정 확인 |

# 교육 중 어려웠던 포인트

- PID1, Namespace와 같은 새로운 리눅스 개념을 배우고 Docker와 어떻게 연결되는 내용인지 이해하는데 어려움이 있었다.
- 컨테이너 네트워크는 개별 개념(IP, 포트, NAT)은 알고 있었지만, Docker 환경에서 이 개념들이 어떻게 함께 동작하는지 이해하는 데 어려움이 있었다.

---

# 실습에서 자주 만난 에러와 배운점

- 컨테이너 실행 시 기본적으로 bridge 네트워크로 동작하는데 포트 포워딩을 설정하지 않아 외부(퍼블릭 주소)에서 접근할 수 없었던 사례가 있었다.
- docker run에서 IMAGE의 앞 뒤로 도커 옵션과 컨테이너 안 명령이 나뉘는데 옵션 순서를 잘못 작성해 컨테이너의 상태가 예상과 달랐던 사례가 있었다.
